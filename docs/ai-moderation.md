# AI event safety moderation and deduplication

The administrator's **Event Management** screen automatically analyzes queued pending events and displays risk flags, a completeness score (0–100), missing information, and likely duplicates from the same organiser. The detail drawer shows evidence, semantic similarity estimates, a suggested description, and a return/rejection reason. Administrators can apply the description or return the submission with the AI reason in one click. Applying a description leaves the event pending and queues a fresh analysis. Publication always requires an administrator's existing approve action.

## Deploy

1. Apply `supabase/migrations/024_add_ai_event_moderation.sql` after the existing migrations. With a linked Supabase project, use `supabase db push` after checking the migration history (the repository already contains two `019` migrations).
2. Configure the same server-side `AI_API_KEY` used by the existing AI features: `supabase secrets set AI_API_KEY=...`. The key is for the existing GLM provider (`glm-4.5-flash`) and must never be a `VITE_` variable.
3. Deploy `supabase functions deploy ai-moderation`. The function's `verify_jwt = false` setting is intentional: the handler itself validates the bearer token with Supabase Auth and checks the active account, role and event ownership before any privileged queries. Only administrators can force a rerun or receive the review details; organisers can trigger analysis for their own pending submission.

The frontend triggers analysis after create, edit/resubmit and draft submission. The database independently records every pending submission, so a missing AI deployment, browser interruption or provider failure cannot lose the review queue. Opening/refreshing the administrator event page processes queued submissions with two concurrent workers; failed items show a retry action. This does not require a database webhook, cron job or an always-open browser to save the queue. Processing the queue does require a submission request or an open administrator event page.

## Assessment and reliability

- Text safety checks cover illegal promotion, off-campus scams/phishing and hate speech, with evidence and severity. English and Chinese are supported. Poster image pixels are not inspected.
- Completeness assigns 20 points each to a meaningful title, date/time and venue/link, plus 0–40 points for useful description content. Short descriptions and test data such as `asdf` receive zero description points even if the provider returns an optimistic score. Missing details and low quality lead to a changes-requested recommendation.
- Semantic comparisons include every eligible same-organiser pending, published or completed event, read in pages of 200 and sent to the model in batches of 10. The event itself and inactive proposals are excluded. Similarity of at least 80 is flagged; the prompt distinguishes separately dated recurring sessions. Similarity is an advisory model estimate, not an embedding cosine score.
- Provider outputs are structurally validated. Unknown event IDs, invalid scores, malformed JSON or a failed comparison batch fail the review rather than showing a partial pass. Model prompts treat submitted event text as untrusted data. Administrators can inspect all suggestions before adopting them.
- Reviews use a server-side content snapshot and a five-minute processing lease. Unchanged completed results are cached. Edits/resubmissions clear old results. Claim and completion RPCs are service-only; browser clients cannot forge review results. Adoption checks the pending state and snapshot inside a transaction, and records the administrator/action/result in `event_ai_review_actions`.
- AI failures never approve or reject an event automatically. Manual moderation remains available. Inputs over 20,000 characters per target text field require manual review. Provider calls share a two-minute analysis budget; an unfinished comparison fails the review without reporting partial findings as a pass.

## Verify

Run `npm run build`, `npm run test:unit -- --run` and `npm run test:moderation-db`. Unit tests exercise scoring, semantic batching, recurring sessions, malformed provider output, queue errors and interface actions. The isolated PGlite PostgreSQL suite runs the actual migration to verify RLS/default grants, queuing, leases, stale results, adoption and audit records without connecting to a Supabase project. Run `deno test --no-lock supabase/functions/ai-moderation/handler_test.ts` and `deno check --no-lock supabase/functions/ai-moderation/index.ts` for the handler's authentication, role/ownership checks, provider failure and stale-completion tests.

After deployment, submit `asdf`, a detailed legitimate activity, a renamed duplicate of the same session and a separately dated recurring session; verify the flags, score and administrator actions. Edit an event during analysis and confirm that its old result cannot be saved or adopted. Verify organisers/students cannot read the AI review tables or use adoption/service-only RPCs. These local suites mock the AI provider; they do not measure live model accuracy or substitute for a deployed end-to-end check.
